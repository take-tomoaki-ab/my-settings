# Pink Elephant Guard

## 目的

修正会話では、削除した案や訂正前の内容がコンテキストに残り続ける。
そのため「もう使わない要素」が、完成稿の見出し、説明、台詞、構図、画像内文字へ再登場することがある。

このスキルは、却下・削除・訂正・禁止された要素を**変更履歴として隔離**し、修正後の**現在状態だけ**から完成物を組み直すための規範である。

目標は禁止語を伏せることではない。
削除跡や言い訳を残さず、現在の目的だけで自然に成立する完成物を返すことである。

成功状態は次のとおり。
利用者が「その案はなし」「これは消して」と修正したあと、完成稿に旧案の単語、言い換え、削除理由、否定形、視覚的な名残が現れず、現在案だけで自然に完成している。

## 適用範囲

次のような、受け手（鑑賞者・利用者）向けの最終出力を作成・修正するときに適用する。

- 広告コピー、SNS 投稿、記事、見出し、CTA
- 台詞、ナレーション、字幕
- 画像生成プロンプト、動画生成プロンプト
- 画像内文字、物体、背景、構図
- UI 文言、ラベル、説明文
- 完成版として配布する要約や資料

隔離対象となる履歴の例。

- 採用しなかった初期案
- 削除を指示された物体、人物、台詞、機能
- 訂正前の数値、名前、設定
- 禁止された表現や方向性
- 「そこではない」と否定された構図や主題

## 適用しない範囲

次の場合、除外対象を隠さない。

- A 案と B 案の比較
- 変更履歴、議事録、監査記録
- 法令、契約、広告開示
- 安全、医療、アレルゲン、リスク説明
- アクセシビリティ表示
- 障害分析、原因調査、再発防止
- 利用者が明示的に必要とした不使用訴求（「カフェインレス」など）

このスキルは、事実、失敗、危険、義務的な開示を見栄えのために隠す仕組みではない。

## 発動条件

### 暗黙発動

次の 3 条件を満たす場合、明示指定がなくても適用する。

1. 会話内に、却下・削除・訂正・禁止された要素がある。
2. 受け手向けの完成物を新規作成または修正しようとしている。
3. 完成物で、その履歴を説明する必要がない。

強い発動例：「これは消して」「その案はなし」「入れないで」「そこじゃない」「企画から外れました」「前の設定は使いません」。

発動判定は文字列一致だけで行わず、依頼全体の意味から行う。
同じ会話で初稿を作ったあと、次のメッセージで削除を指示された場合も発動する。

### 非発動

次のいずれかに該当する場合、暗黙発動しない。

- 完成物の制作ではなく、比較、監査、原因分析を求めている。
- 旧案や除外対象を記録へ残すことが成果物の要件である。
- 法務、安全、アクセシビリティ、契約上の理由で明示が必要である。
- 訂正履歴が存在しない通常の新規制作である。

非発動と判定したときは、種別に応じて次を最小要件とする。

すべての非発動に共通する要件。

- 却下要素を原文のまま残す。伏字、言い換え、省略をしない。
- 却下側を隠した版を成果物として出さない。
- 後述の「処理工程」と「検収基準」は適用しない。どちらも発動時のみの規範である。

比較、監査、記録、原因分析のとき、これに加えて次を満たす。

- 却下理由・変更経緯を明記する。

法令、安全、アレルゲン、アクセシビリティ上の必要表示のとき、加えるのは次であり、変更経緯は書かない。

- 表示内容を、省略、弱め、脚注化、婉曲化しない。脚注化とは、本文より小さい文字、注記記号への追い出し、折りたたみ、別ページへの分離を指す。同じ面にあり本文と同じ文字の扱いなら、※ 記号を伴っても脚注化ではない。
- 必要な表示が未確定のまま残る場合、推測で埋めず、未確定であることを示す。この未確定の明示は開示面そのものに置く。工程 4 の「未検査の範囲は成果物本体に書かない」は発動時の規定であり、ここには適用しない。

### 非発動の適用単位

まず成果物の全体を見る。
全体が比較、監査、記録であるときは、成果物ごと非発動として扱う。

全体としては受け手向けの完成物だが、その内部に記録・開示が必要な面を含むときは、面ごとに判定する。
完成面は発動、開示面は非発動とし、開示面の内容を完成面へ流し込まない。
開示面は `VISIBLE_EXCEPTIONS` で処理しない。独立した非発動の面として扱う。

完成面から開示面への参照（「アレルギー表示欄をご確認ください」など）は、媒体の慣習や法令が求める場合に置く。
参照を置くときは、開示内容そのものを完成面へ書かず、参照先の名前だけにとどめる。
求められていない場合は置かない。

`VISIBLE_EXCEPTIONS` は、発動した完成面の内部に部分的に残す要素に限る。

### 優先順位

判断が競合するときは、次の順で優先する。

1. 法令、安全、契約、アクセシビリティ上の必要表示
2. 利用者が完成面へ明示するよう指定した内容
3. 利用者が最後に確定した現在状態
4. それ以前の案や変更履歴

## 入出力契約

会話から次の 4 つを受け取る（内部的な分類であり、利用者へ提示するものではない）。

| 名前 | 内容 |
|---|---|
| `TARGET_STATE` | 修正後に存在し、伝えるべき現在状態 |
| `REJECTED_HISTORY` | 取り下げた案、削除対象、誤り、修正理由 |
| `VISIBLE_EXCEPTIONS` | 完成面へ残す必要がある比較、開示、不使用訴求 |
| `SURFACE` | 受け手が見る見出し、本文、台詞、画像、UI、ナレーション等 |

利用者が「必ず残せ」と指定した要素のうち、却下履歴と無関係なもの（必要なヘルプ、状態説明、必須の仕様）は `TARGET_STATE` に入れる。
`VISIBLE_EXCEPTIONS` は、却下履歴に由来する要素を完成面へ残す場合に限る。

不使用訴求（「カフェインレス」「無糖」など）は、却下履歴に由来するなら `VISIBLE_EXCEPTIONS`、履歴と無関係な商品仕様なら `TARGET_STATE` に入れる。
どちらの箱でも完成面へ残す点は同じであり、帰属の判断に時間をかけない。

出力は次の条件を満たす完成物とする。

- `TARGET_STATE` だけで自立している。
- `REJECTED_HISTORY` を主題にしていない。
- `VISIBLE_EXCEPTIONS` だけを、指定範囲内で保持している。
- 削除跡、伏字、言い訳のように見えない。
- 「完成稿だけ」と指定された場合、検査報告を添えない。

## 処理工程

以下は発動時の工程である。非発動と判定した場合は、この節と「検収基準」に進まず、「非発動」節の最小要件に従う。

### 工程 0: 発動判定を先に確定する

「発動条件」に照らして、発動 / 非発動を先に決める。
成果物に完成面と開示面が混在する場合は、面ごとに判定してから工程 1 へ進む。

### 工程 1: 現在状態と例外を分離する

会話を `TARGET_STATE`、`REJECTED_HISTORY`、`VISIBLE_EXCEPTIONS`、`SURFACE` に分類する。

不在自体を訴求するかどうかで完成物が大きく変わり、かつ会話から判断できない場合だけ質問する。
それ以外は現在状態を優先して進める。

### 工程 2: Clean Brief を作る

`TARGET_STATE`、許可された事実、媒体、トーン、必要な構造だけで、内部用の brief を組み直す。

- **MUST**「X を出さない」ではなく、X がなくても成立する肯定形で書く。
- **MUST** 却下理由や元案を、生成用 brief へ再投入しない。

削除後の空白は、次の順で埋める。

1. **MUST** まず構成の組み替えで埋める。情報の順序、見出しの立て方、段落や画面の区切り、構図の重心を、現在の目的に合わせて組み直す。
2. **MUST** それでも足りない分を内容で埋める場合、材料は `TARGET_STATE` と会話で確認済みの事実に限る。新しい効能、実績、数値、仕様、比較を作らない。
3. **MUST** 材料が足りないときは、作らずに短い完成物にする。短さは欠陥ではない。削除跡を隠すことと、書いていない主張を足すことは別である。字数上限は埋めるべき枠ではない。
4. **MUST** 媒体上は必須だが確定していない情報（税込か税抜か、日付、連絡先、正式名称）は、推測で埋めず完成面から省く。未確定であることは利用者への報告に書く。完成面に未確定の注記を置かない。開示面の扱いは「非発動」節が別に定める。

媒体上の定型句（挨拶、結び、CTA の常套句）、操作の案内、問い合わせ導線、トラブルシュートの手順は、成果物の主張ではない。
これらは媒体の慣習として置いてよく、上記 2 の「作らない」には当たらない。
利用者に必要な案内、ヘルプ、状態説明を、この規定を理由に削ったり弱めたりしてはならない。

案内や手順が前提にしてよいのは、媒体、外部サービス、一般的な受信環境について広く成立する事実である（迷惑メールへの振り分け、外部アプリ側の通知設定など）。
成果物の対象そのものについては、確定していない機能名、設定項目、挙動、権限を書かない。
連絡先や窓口名が未確定なら、名称を作らずに導線だけを置く。

確定した仕様から一般に導ける描写、食感や見た目の説明、用途の提案は「主張」ではない。書いてよい。
「主張」に当たるのは、確定情報の外にある効能、実績、数値、比較優位、産地、受賞、安全性である。
判断は、その記述が外れたときに事実の誤りになるかで決める。誤りになるなら書かない。

### 工程 3: 現在状態から生成する

Clean Brief だけを制作上の正本として初稿を作る。
修正前の文章から数語を削る方式は採らない。現在状態を主語にして最初から組み直す。

### 工程 4: Pink Elephant Scan を行う

初稿の `SURFACE` 全体を、次の 5 層で検査する。

| 検査 | 確認内容 |
|---|---|
| Literal leak | 却下語、表記揺れ、画像内文字、ラベル |
| Semantic leak | 同義語、上位語、言い換え、否定形、婉曲表現 |
| Rationale leak | 削除理由、「代わりに」「以前は」などの変更説明 |
| Attention leak | 不在や比較が、見出し・冒頭・CTA・結論の主題になっていないか |
| Visual leak | 削除物、輪郭、破片、影、容器、持ち手、プレースホルダー |

Semantic leak は、語幹や字面の一致では判定しない。
その語を読んだ受け手が却下要素を想起するかどうかで判定する。
現在状態を説明するために必要な一般語は、却下要素と語を共有していても leak ではない。
過剰な言い換えで現在状態の説明が不正確になること、必要な語を失うことは、それ自体が欠陥である。

想起するかどうかで決まらない境界例は、次の順で決める。

1. その語を外すと現在状態の説明が不正確になる、または受け手に必要な情報が失われるなら、残す。
2. 外しても説明が成立し、情報が失われないなら、外す。

判定が揺れること自体は欠陥ではない。この順で決めて先へ進み、迷いを成果物へ持ち込まない。

利用者が確定した現在状態の語は、却下要素の対偶に見えても残す（却下が「氷入り」で現在が「常温」の場合の「常温」など）。
却下要素の不在を指すために新しく持ち出した語だけを leak として扱う。

どの層が該当するかは媒体で決まる。
文章では Visual leak を検査しない。
UI では版面上の残留（空欄、無効ラベル、プレースホルダー、項目枠）として検査する。
画像と動画では画素・フレーム上の残留として検査する。
画像・動画のプロンプトを書く段階で検査できるのは、プロンプト文面に削除物、容器、プレースホルダー、旧案の表示文字が書かれていないかまでである。
媒体に存在しない層だけを省略する。

検査済みと報告できる範囲は、自分が生成した成果物そのものに限る。

- 自分が書いた文言、構造、プロンプト文面は、検査して検査済みと報告してよい。
- 自分が確認していない実物（レンダリングされた画面、生成画像の画素、生成動画のフレームと音声）は未検査として扱い、検査済みと報告しない。
- 省略した層も検査済みと報告しない。

未検査の範囲は、利用者への報告に書く。成果物本体には書かない。
未検査の範囲が存在しない媒体では、報告も不要である。
「完成稿だけ」と指定された場合、未検査の注記も成果物へ添えない。

工程 2 で足した内容も検査対象に含める。`TARGET_STATE` から導けない主張が混じっていれば FAIL とする。

`VISIBLE_EXCEPTIONS` は、指定された場所、目的、範囲でのみ許可する。

### 工程 5: 汚染した初稿を捨てて再生成する

本工程は、工程 4 の Scan が FAIL したときの規定である。
工程 3 で初稿を書いている途中の推敲、語の選び直し、書きかけの破棄は「修理」に当たらない。制約なく行ってよい。

Scan が FAIL した場合、漏れた単語だけを消して修理してはならない。
説明構造や構図自体が旧案中心になっている可能性があるため、工程 2 の Clean Brief から再生成し、再度 Pink Elephant Scan を行う。
再生成の単位は、漏れが見つかった面（段落、ブロック、構図の要素、画面のセクション）を含む範囲とする。成果物の全体を毎回捨てる必要はない。

## 媒体別要件

### 文章

- 見出し、冒頭、本文、CTA、脚注まで検査する。
- 「廃止しました」「現在はありません」など、不在の説明を安易に置かない。
- 差分報告を求められていない限り、変更経緯を完成稿へ出さない。

### 画像生成プロンプト

- 現在必要な被写体、形、配置、素材、光、接触関係を肯定形で記述する。
- 却下物を長い negative prompt として再列挙しない。
- 表示文字、ラベル、背景小物の残留は、工程 4 の Visual leak として検査する。検査できる範囲と報告できる範囲の定義は工程 4 を正本とする。

### 動画生成プロンプト

- 現在必要な被写体、因果、動作、カメラ、編集、音、文字、最終フレームを定義する。
- 旧案の出来事を「起こらない出来事」として脚本へ残さない。
- 音だけに警報、失敗音、旧案の台詞が残っていないか確認する。
- フレームおよび音声上の残留は、工程 4 の Visual leak として検査する。検査できる範囲と報告できる範囲の定義は工程 4 を正本とする。

### UI とラベル

- 非表示にした機能名の残留（空欄、無効ラベル、プレースホルダー、項目枠）は、工程 4 の Visual leak として検査する。検査内容の定義は工程 4 を正本とする。
- 項目の総数に言及しない。会話で総数を確定された場合も、成果物では数に触れない。数を数えると、以前の項目数との差分が読み手に伝わる。
- 設定画面という媒体の前提から導ける操作（項目のオンとオフ、保存、取り消し、再読み込み）は書いてよい。UI 部品の形状（トグル、チェックボックス、プルダウン）が未確定なら、形状に依存しない語で書く。
- 変更履歴画面や管理者向け監査画面は、非発動対象として扱ってよい。
- 利用者へ必要なエラー、安全表示、状態説明は消さない。

## 検収基準

本節は発動時にのみ適用する。非発動と判定した成果物へ Pink Elephant Scan をかけてはならない。

次の 10 条件を満たしたとき PASS とする。

- `VISIBLE_EXCEPTIONS` にない却下要素の語句が 0 件。
- 同義表現、否定形、婉曲表現による意味残留が 0 件。
- 削除理由、変更説明、不在の強調が 0 件。
- タイトル、冒頭、CTA、結論が現在の目的を主題にしている。
- UI では、版面に空欄、無効ラベル、プレースホルダー、項目枠の残留がない。
- 画像または動画では、確認可能な範囲に視覚・音声残留がない。
- 例外表示が、指定された場所・目的・範囲を越えていない。
- 未確認の媒体を検査済みと報告していない。
- 完成物が削除跡に見えず、現在案だけで自然に成立している。
- `TARGET_STATE` と確認済みの事実から導けない主張を足していない。

媒体に該当しない条件は判定から除く。除いた条件を満たしたとは報告しない。

## 使用例

### 通常の修正

入力：
> 初期案の桜あんぱんと無料配布は企画から外れました。現在はクロワッサン 3 種と自家焙煎コーヒーの朝フェアです。完成告知だけを書いてください。

期待動作：

- 桜あんぱん、無料配布、企画変更の説明を完成稿へ出さない。
- クロワッサン、コーヒー、開催時間を主役にして自然な告知を作る。

### 必要な不使用訴求

入力：
> 「カフェインレス」が購入理由です。過去の通常版の検討経緯は不要ですが、完成コピーには「カフェインレス」を 1 回入れてください。

期待動作：

- 「カフェインレス」を `VISIBLE_EXCEPTIONS` として保持する。
- 通常版や検討経緯は完成稿へ出さない。

### 比較監査（陰性対照）

入力：
> A 案と B 案の違いを監査記録として残してください。両案の固有要素を省略しないでください。

期待動作：

- 発動しない。
- A 案、B 案、変更理由を必要な範囲で明記する。

## 既知の限界

- 発動は意味判定であり、決定論的ではない。
- 会話コンテキストから旧案を物理的に削除するものではない。
- モデル、会話長、競合する指示によって結果が変わる。
- テキストの画像・動画プロンプトは検証済みだが、生成画像の画素と生成動画のフレームは未検証。
- 長い複数ターン会話、コード変更、法務・安全表示の全類型は未検証。

## 運用上の注意

- 受け手向けのコピー、台詞、画像・動画プロンプトでは暗黙発動を前提にする。
- 監査、変更履歴、コード、法務、安全では、明示発動または非発動を基本にする。
- 誤発動が疑われる場合は、成果物の目的と `VISIBLE_EXCEPTIONS` を先に固定する。
- このスキル内へ、会話全文、顧客情報、秘密、個人環境のフルパスを保存してはならない。
