# pr-review-autopilot スキル

## 概要

**複数の PR を並行で走らせながら、レビュー対応・衝突解消・マージを自律的に進めるための運用スキル。**

目的は 1 つに絞られる。**人間がポーリングしないこと。**
「レビュー来てないかな」と人間が見に行く運用をやめ、来たときにこちらが動く運用にする。

このスキルは 2026-08 に実運用した記録から作られている。
**設計だけでなく、同じ構造の失敗を 4 回繰り返した記録も含む。**そちらのほうが価値がある。

## いつ使うか

- 複数の PR が同時にレビュー中で、着弾のたびに人間が起こされている
- PR をスタック（親子）で積んでおり、親のマージが子を壊す
- タスクランナー（ToRide 等）で複数の Claude セッションを回しており、投入判断を人間がしている

**単一 PR に 1 件のレビューが来ただけなら、このスキルは要らない。** `/review-respond` で足りる。

## 前提

| 要素 | 役割 |
| --- | --- |
| `gh` CLI（GraphQL が叩ける状態） | PR の状態取得。REST では未解決スレッド数が取れない |
| オーケストレーター（このセッション） | 起票・投入・検証・マージの判断。**コードは読まない** |
| タスクランナー（ToRide 等）+ 実行セッション | 実作業。ペイン数ぶん並行する |
| バックグラウンド監視スクリプト | 状態変化を検知してオーケストレーターを叩き起こす |

**オーケストレーターはコードを読まない。**調査が必要なら調査タスクを立てる。
コンテキストを実装の詳細で埋めると、全体の判断ができなくなる。

## 1. 中核 — ハーネスの再呼び出しを起床に使う

**これが仕組み全体の要である。**

Claude Code でバックグラウンドコマンドを走らせると、**そのコマンドが終了したときにハーネスがセッションを再呼び出しする。**
つまり、監視スクリプトの `exit` がそのままオーケストレーターの起床トリガーになる。

```
監視スクリプトが「起こすべき状態」を検知 → exit 0
        ↓ ハーネスがオーケストレーターを再呼び出し
オーケストレーターが状況を確認して次の手を打つ
        ↓
監視を張り直す
```

**ポーリングではない。**オーケストレーターは寝ていて、監視が起こしたときだけ動く。

```bash
# 起動はこれだけ
Bash(command="bash <scratchpad>/review-watch.sh 180 720", run_in_background=true)
```

`180` = 監視間隔（秒）、`720` = 最大稼働時間（分）。

## 2. 🔴 最重要 — 「状態」で起こしてはいけない

**このスキルで唯一、読み飛ばしてはいけない節。同じ構造のミスを 4 回した。**

### 何が起きるか

状態ベースの起床条件は、**その状態が続く限り毎サイクル鳴り続ける。**

1 回目。`PANE_FREE` を「ペインが空いている」で判定した。
→ **投入できるタスクが無い間、ずっと鳴った。**

2 回目。直したつもりで `NEEDS_CONFLICT_FIX` を「approve>=1 かつ CONFLICTING」で判定した。
→ **衝突が解消されるまで毎回鳴った。**同じ構造のミスである。

### 対策

**状態ベースの起床条件には、必ず「まだ対応していない」の判定を組み合わせる。**

```bash
# ❌ 悪い例 — 状態が続く限り鳴り続ける
[ "$mrg" = "CONFLICTING" ] && WAKE=1

# ✅ 良い例 — 「まだタスク化していない」を組み合わせる
HANDLED=$(sqlite3 "$DB" "select count(*) from tasks
  where status in ('will_do','doing') and title like '%#$n%'")
[ "$mrg" = "CONFLICTING" ] && [ "$HANDLED" -eq 0 ] && WAKE=1
```

### 「増えた」で起こし、「減った」では起こさない

同じ発想である。未解決スレッドが 7 → 1 に減るのは**対応が進んだ証拠**なので、起こす必要がない。

```bash
[ "$th" -gt "$oth" ] && HIT="NEW_THREAD:#$n(${oth}→${th})"   # 増加のみ
```

### 3 回目・4 回目 — 待ち行列は「列挙」ではなく「除外」で数える

3 回目。待ち行列を「全部の `will_do`」で数えた。
→ **別担当ぶんや、実データ待ちで着手できないタスクまで数え、空きペインのたびに空回りした。**

4 回目。「PR 番号を含むタスクだけ数える」（`title like '%#1%'`）に変えた。
→ **新しく作った調査タスクが数えられず、ペインが空いても起きなかった。**

**最終形はこうである。**

```sql
-- 「投入できるものを列挙」ではなく「投入できないものを除外」
title not like '[Task %' and title not like '[S5]%' and title not like '[S6]%'
```

**新しく作ったタスクが黙って無視されるより、余分に起こされるほうがマシだからである。**
フェイルセーフの向きを間違えないこと。

### 「発火しない条件」はバグに気づけない

`STALL` 検出（`doing` なのにプロセスが死んでいる）が、**数週間まったく発火していなかった。**
PID の取得先を間違えていた。

```sql
-- ❌ tasks.data に pid は入っていない（常に空）
select json_extract(data,'$.pid') from tasks ...

-- ✅ task_runtime テーブルと join する
select t.title||'|'||coalesce(r.pid,'') from tasks t
  left join task_runtime r on r.task_id = t.id
  where t.status='doing' and t.pane in ('main','sub')
```

**起床条件を書いたら、一度は意図的に発火させて確認すること。**

## 3. 監視スクリプトの構成

`assets/` に雛形がある。**scratchpad にコピーして `autopilot.env` を書けば動く。**

| ファイル | 役割 |
| --- | --- |
| `autopilot.env.example` | 設定。owner / repo / 監視対象 PR / 自分の login / bot 名 / DB パス |
| `snapshot.py` | 担当 PR ごとに状態を **1 行ずつ**出す |
| `review-watch.sh` | 監視ループ本体。差分と条件を見て `exit 0` |
| `review-watch.state` | 前回のスナップショット。**外部から kill されても引き継げる**（自動生成） |
| `review-watch.lock` | 二重起動の防止（自動生成） |
| `pr-scan.sh` | 未解決スレッドの中身を展開する。オンデマンド |
| `issue-comments.sh` | `reviewThreads` に出ない issue コメントを列挙する。オンデマンド |
| `dash.sh` | ペイン占有 / PR 状態 / 未返信コメント / 未着手タスクのダッシュボード。オンデマンド |
| `task-prompt-template.md` | 委譲タスクのプロンプト雛形 |

### snapshot が 1 行 1 PR の固定長フォーマットである理由

**シェルの `while read` でそのまま読めるからである。**
JSON にすると `jq` を挟む必要があり、`state` との差分比較も面倒になる。

```
175 0 1 1 main CONFLICTING SUCCESS
176 0 0 0 main MERGEABLE   SUCCESS
178 1 0 0 main CONFLICTING SUCCESS
```

順に `<番号> <未解決> <他人コメント> <approve数> <base> <mergeable> <CI>`。

**approve 数は自分と bot を除外して数える。**
`greptile` / `github-actions` / `devin` / `linear-code` / `coderabbit` などは除く。
**自分の approve でマージが走ったら事故である。**

**取得に失敗した PR は行を出さない。** 0 を出すと「減った」→次に「増えた」で二重に鳴る。

### 監視対象 PR には自分の担当ぶんだけを入れる

別担当の PR やマージ済みの PR を入れると、**自分では対応できない起床**が発生して空回りする。

## 4. 起床条件（優先順）

| # | 条件 | 発火する状況 |
| --- | --- | --- |
| 1 | `READY_TO_MERGE` | **base=main / approve>=1 / 未解決=0 / MERGEABLE / CI=SUCCESS** の 5 条件がすべて成立 |
| 2 | `PANE_FREE_WITH_QUEUE` | **投入できる待ち行列がある状態で**ペインが空いた |
| 3 | `REVIEW_ARRIVED` | 未解決スレッド / 他人の issue コメントが**増えた** |
| 4 | `NEEDS_CONFLICT_FIX` | **approve>=1 なのに CONFLICTING、かつ未タスク化** |
| 5 | `STALL` | `doing` なのに claude プロセスが死んでいる |

**優先順が意味を持つ。**同時に成立したら上から 1 つだけ出して終了する。
起きたオーケストレーターが最初にやることは「一番マージに近いもの」であってほしいからである。

## 5. kill 耐性

**バックグラウンド監視は 45〜50 分程度で外部から kill されることがある。**対策は 2 つ。

1. **`state` ファイルに前回のスナップショットを書く。**プロセスが死んでも、張り直したときに続きから比較できる
2. **`lock` ファイルで二重起動を防ぐ**

一度、`&` と `run_in_background` の両方で起動してしまい、
**2 つの監視が同じ state を取り合って検知を取りこぼした。**

```bash
if [ -f "$LOCK" ] && kill -0 "$(cat "$LOCK" 2>/dev/null)" 2>/dev/null; then
  echo "ALREADY_RUNNING pid=$(cat "$LOCK")"; exit 4
fi
echo $$ > "$LOCK"
trap 'rm -f "$LOCK"' EXIT
```

**起動経路は 1 系統に統一すること。**

## 6. タスクへの委譲プロトコル

### 起動直後に必ず SendMessage を送る

**これは事故から生まれた運用である。**

最初、プロンプトに「完了したらオーケストレーターに知らせて。届いていなければ `ListAgents` で探して」と書いた。
**結果、担当が宛先を推測し、まったく無関係の別セッションに完了報告を送った。**
セッション名は連番形式で、この時点で 56 個あった。

**現在の運用。**

1. `start_task` した直後に、オーケストレーターから **必ず** SendMessage を送る（有効な `from` を担当の手元に置く）
2. プロンプトには **「その `<cross-session-message from="...">` の `from` 属性をそのまま `to` に指定して返信してください。宛先を推測しないでください。私からのメッセージが届くまで待ってください」** と書く
3. 保険として `<taskid>_DONE` ファイルを作らせる（通知が失われた場合に検出できる）

**起動直後の SendMessage には、プロンプト記載後に変わった情報を必ず載せる。**
タスクのプロンプトは起票時に書くので、投入時には陳腐化していることがある。
実際「#174 はマージ直前」と書いたプロンプトを、投入時に「もうマージ済み」と訂正した。

### タスクを自分で done にさせない

**プロンプトに「タスクを自分で done にしないでください」と必ず書く。**
完了判定はオーケストレーターがする。担当は報告するだけ。

### `start_task` は resume しない

**ToRide の `start_task` は毎回新しいセッション ID で起動する。**したがって、

- **`done` を `will_do` に戻して `start_task` するのは禁じ手。**セッション ID が変わり、元のセッションを再開できなくなる
- **追加の依頼は SendMessage で送る。**タスクを作り直さない

### プロンプトに作業ディレクトリをハードコードしない

**割り当てられた作業ツリーと食い違うと事故になる。**
「割り当てられた作業ディレクトリでそのまま作業してください。自分で `git worktree add` しないでください」と書くだけにする。

## 7. マージ前の独立検証 — 報告を鵜呑みにしない

**担当から「マージして大丈夫です」と来ても、そのままマージしない。**

```bash
# 1. GraphQL で条件を確認する
#    mergeable / mergeStateStatus / reviewDecision / 未解決スレッド数 / CI rollup / approve の主体
gh api graphql -f query='...'

# 2. diff の「削除行」を直接見る
gh pr diff <N> | grep -E "^-[^-]" | grep -E "<main 側にしかない識別子>"
```

**`typecheck` が通るだけでは巻き戻しを検出できない。**
型が合っていても、main 側の実装を消していれば通ってしまう。
**削除行を目で見るのが唯一確実な方法である。**

実際、ある PR では main 側にしか無い 3 つの識別子が削除行に 1 件も無いことを確認してからマージした。

**approve の主体も確認する。**自分の approve でマージが走らないように。

## 8. スタック PR × squash merge の宿命

**squash merge 運用のリポジトリで PR をスタック（親子）で積むと、親のマージで子は必ず CONFLICTING になる。**
同じ変更が「親の元コミット群」と「main の squash コミット 1 個」の 2 通りで存在するからである。

```
main
 └ #174 (approve 2)
    ├ #175 (approve 1)
    └ #178
       ├ #179 └ #182
       └ #181
```

**1 日で 3 回起き、それぞれ解消に丸ごと 1 タスクかかった。**

### 運用ルール

- **main に近い順にマージする**（レビュー中の PR の差分を途中で増やさないため）
- **親をマージしたら、子の base を張り替える**

```bash
gh api -X PATCH /repos/<owner>/<repo>/pulls/<N> -f base=main
```

- **衝突解消は「差分を増やさない」タスクとして切り出す。**approve 済みの PR に手を入れると approve が無効になる

### 衝突解消の「3 段確認」

**`add/add` の衝突で「ブランチ側を捨ててよいか」を確定させる手順。**

1. **そのファイルを触ったブランチ側のコミットを特定する。**独自コミットが別のファイルしか触っていなければ、ブランチ側に固有変更は無い
2. **その独自コミットが親ブランチの祖先であることを確認する**
3. **`git diff --stat origin/<親ブランチ> origin/main -- <対象ディレクトリ>` が空**であることを確認する = squash が忠実だったと確定できる

**ハンクが重なっていない場合は `git apply --3way` で合成できる。**片方を捨てる必要はない。

### `git merge-tree` で下流への影響を事前実測する

ある担当が、コメント 1 行を直そうとして `git merge-tree` で試算したところ、
**その 1 行だけが下流 2 本の両方に衝突を生むと判明した。**

→ **あえて 1 バイトも触らずに残し、下流は両方クリーンのままにした。**

**「直したほうが綺麗」より「下流が衝突しない」を優先する。**並行作業では有効である。

## 9. プロンプト設計で効いたこと

雛形は `assets/task-prompt-template.md`。以下はその設計理由。

### 決定済みの方針は、担当に判断させない

**レビュアーの提案をそのまま採らせたくない場面がある。**

例。レビュアーが「`description` に『現在は段階 1〜3 のみ実装』と書け」と提案した。
しかし段階は現在進行形で増えており、書くと PR がマージされるたび手で書き換える運用になる。
さらに兄弟 PR が既に「番号を書かず実装状況表を参照する」対応を済ませていた。

→ プロンプトに **「レビュアーの提案をそのまま採らないでください（方針はオーケストレーターが決定済み）」**と書き、理由を 2 つ添えた。
**同時に「指摘の趣旨は満たしてください。『対応しない』という選択はしないでください」とも書いた。**

**担当が知り得ない横断的な事情は、オーケストレーターが判断して渡す。**
担当が判断できることは担当に任せる。**この切り分けが重要。**

### 「止まってよい」と明示する

> **判断に迷ったら、勝手に決めずに報告してください。**
> **差分に確信が持てない場合は、push せずに報告してください。急がなくていいです。差分を壊すよりずっとマシです。**

**急がせないと明言することが、雑な判断を防ぐ。**

### 踏むと痛い実務注意を毎回コピーする

**「一般論として危ない」ではなく「このリポジトリで実際に起きた」ものに絞ると、読まれる。**
実例は `assets/task-prompt-template.md` を参照。

### 申し送りは result.md に書かせる

各タスクに `<taskid>_result.md` を書かせ、次のタスクのプロンプトから読ませる。

> 次のタスクの担当は、このファイルだけを読んで作業を始めます。そのつもりの粒度で書いてください。

**「後続が直接使うエクスポート（コンポーネント名 / props / 関数シグネチャ / import パス）」を明示的に要求する。**
これが無いと、後続が自前で調べ直す。

## 10. オーケストレーター自身のメモリ

**`plan.md` に全経緯・方針・申し送りを追記していく。**

**セッションのコンテキストは有限で、要約されると細部が落ちる。**`plan.md` は落ちない。
**各タスクのプロンプトの冒頭で必ず `cat` させる。**

書く内容。

- 現在の稼働状況（どのペインで何が動いているか）
- PR ごとの状態表（未解決 / approve / base / mergeable）
- **決めた方針と、その理由**
- **踏んだ失敗と、その是正**
- ユーザーからの指示で、後から効いてくるもの

**「決めた理由」を書くのが重要。**理由が無いと、状況が変わったときに再判断できない。

---

## 11. ユーザーに訊く / 訊かない

**判断が「構造から一意に決まる」なら訊かない。「価値判断が要る」なら訊く。**

| | 例 |
| --- | --- |
| **訊いた** | 別担当の PR が、こちらのマージの巻き添えで CONFLICTING になった（「触らない」と「approve 済みは解消してマージ」の 2 指示が衝突したため）。回答は「触らないで、担当者に任せて」だった |
| **訊いた** | レビュー指摘への対応方針が、設計書やデータスキーマを変える場合 |
| **訊かず決めた** | 申し送り 2 件を別 PR のレビュー対応に統合する（一方は approve 2 件持ちで触ると再レビュー、他方は approve 0 で失うものが無い。かつ既に一度先送りしており二度目を避けたかった） |
| **訊かず決めた** | 衝突解消タスクの投入順（親から順、という構造上の制約） |

**訊かずに決めたものは、決めた理由を `plan.md` に書く。**

## 12. 立ち上げ手順

### Step 1: scratchpad にスクリプトを展開する

```bash
SP="<scratchpad>"          # セッションの scratchpad ディレクトリ
SRC="<このスキルの assets>"
cp "$SRC"/{snapshot.py,review-watch.sh,pr-scan.sh,issue-comments.sh,dash.sh} "$SP/"
cp "$SRC/autopilot.env.example" "$SP/autopilot.env"
chmod +x "$SP"/*.sh "$SP/snapshot.py"
```

### Step 2: `autopilot.env` を埋める

**`AP_PRS` には自分の担当ぶんだけを入れる。**`AP_SELF` は必ず自分の GitHub login にする。

### Step 3: 動作確認する（省略しない）

```bash
cd "$SP" && . ./autopilot.env && python3 ./snapshot.py
```

**1 行 1 PR で出ることを確認する。**空なら `gh auth status` と `AP_REPO_DIR` を確認する。

```bash
"$SP/dash.sh"     # ダッシュボードも一度見て、現況を把握しておく
```

### Step 4: 起床条件を意図的に発火させる

**「発火しない条件」はバグに気づけない。**
`review-watch.state` の数値を手で小さく書き換えて、`REVIEW_ARRIVED` が出ることを確認する。

### Step 5: 監視を張る

```bash
Bash(command="bash <scratchpad>/review-watch.sh 180 720", run_in_background=true)
```

**`&` を付けない。`run_in_background` だけを使う。**両方使うと二重起動になる。

### Step 6: 起こされたら

1. 出力された起床理由（`READY_TO_MERGE` / `REVIEW_ARRIVED` など）を読む
2. 必要なら `pr-scan.sh` / `issue-comments.sh` で中身を展開する
3. 判断して手を打つ（タスク起票・投入・マージ）
4. **`plan.md` に「何を決めたか」と「その理由」を追記する**
5. **監視を張り直す**（Step 5 と同じコマンド）

### Step 7: 空回りしたら、即座に直す

**最初から完成形を書こうとしない。**
空回りしたら原因を `plan.md` に書いて、その場で監視スクリプトを直すほうが速い。
